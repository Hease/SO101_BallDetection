# 데모 시나리오 — 납땜 모사

**총 10분.** 위험한 것(도달 한계·딜레이)은 시뮬·print 드라이버로, 설득력이 필요한
것(비전 서보·티칭·E-STOP)은 실물로 보여준다.

> ⚠️ **인두기는 가열하지 않은 더미다.** 시연 내내 전원을 꽂지 않는다. 이 데모가
> 보여주는 것은 열이 아니라 **팁을 타겟에 정확히 갖다 대는 제어**다.

## 무엇을 하는가

인두기를 집게에 **테이프로 강체 고정**해 두고, 탑다운 카메라가 **인두기 팁 마커**와
**타겟(드라이버 끝) 마커**를 함께 본다. 두 점을 `H`로 로봇 평면 xy 로 바꿔 **오차만큼
팔을 움직이는 폐루프**로 팁을 타겟 위에 올린 뒤, 부하가 뛸 때까지 내려가 **접촉**한다.

인두기를 "집는" 동작은 하지 않는다. 파지 편차가 팁 오차를 지배하기 때문에 그
변수를 통째로 없앴다 — 자세한 결정 이력은 [`solder/README.md`](../solder/README.md) §1.

---

## 준비 (시연 전날 / 당일 아침)

```bash
./hp60c-camera/scripts/start_bridge.sh      # 'Streaming started' 확인
python -m sorting.calib report              # 미측정 값이 없는지 확인
ls data/H.npy                               # 픽셀→로봇 변환이 있는지
```

`calib report` 가 전부 ✅/✏️ 면 준비 끝. ⚠️ 가 남아 있으면 그 줄에 적힌 명령으로
재고 시작한다. **이 확인을 건너뛰면 데모 중에 "왜 안 움직이지"가 된다.**

납땜 전용으로 추가 확인할 것:

| 확인 | 명령 / 방법 |
|---|---|
| 마커 두 색이 잡히는가 | `python vision/lab_tuner.py` → `TIP_LAB`/`TARGET_LAB` |
| 접촉 부하 임계 | 하강 로그의 "부하상승"을 보고 `safety.LOAD_CONTACT` 확정 |
| 서보 게인 부호 | preview 에서 오차 화살표 방향 확인 → 발산하면 `GAIN` 부호 반전 |

빈 작업면에서 **E-STOP 이 실제로 듣는지 먼저 확인**한 뒤 인두기를 고정한다.

## 장면 1 — 작업영역을 손으로 가르친다 (1분 30초) · 실물

> "로봇이 어디까지 가도 되는지를 저희가 숫자로 정하지 않았습니다. 직접 재게 했습니다."

```bash
python -m sorting.teach limits
```

토크가 꺼지고 팔이 자유로워진다. **안전하다고 판단하는 범위의 테두리를 손으로
천천히 한 바퀴** 돌면, 10Hz 로 손끝 좌표가 기록되어 그 모양 그대로 영역이 된다.

말할 것: 운동학 IK 는 반경 0.44m 까지 잔차 0mm 로 푼다. 즉 IK 만 믿으면 한계가
사실상 없다. 하지만 그렇게 뻗은 자세는 서보 부하가 크고 정밀도가 떨어진다 —
**인두기를 들고 있으면 더 그렇다.** 운동학적 한계와 운용상 안전 한계는 다르고,
후자는 재야 안다.

→ 요구사항 **teaching**, **로봇 제어 limit** 의 근거를 여기서 만든다.

## 장면 2 — 좌표계를 가르친다 (1분) · 실물

```bash
python vision/03_calib_auto.py      # 픽셀 → 로봇 평면 H
python vision/lab_tuner.py          # 팁·타겟 마커 Lab 측정
python -m sorting.teach heights     # 팔끝을 작업면에 대고 Enter
```

화면 오른쪽 상태창에 **"미측정 값 N개"** 가 줄어드는 걸 보여준다.

말할 것: 사람이 가르친 좌표와 카메라가 본 좌표가 **같은 좌표계에서 만난다.**
이게 있어야 다음 장면의 "오차 몇 mm"가 픽셀이 아니라 **밀리미터**로 나온다.

→ 요구사항 **좌표 기반 제어**.

## 장면 3 — 측정이 실패하면 (1분) · 실물

> "현장에서 서보가 말을 안 들으면 어떻게 하죠?"

일부러 실패 상황을 만들거나(케이블 분리) 이미 겪은 상황을 이야기한 뒤:

```bash
python -m sorting.calib set robot.z_grasp 0.008 --note "서보4 무응답 — 자로 측정"
python -m sorting.calib report        # ✏️ 수동 으로 표시되고 사유가 남는다
```

말할 것: 자동 측정이 막혀도 **막히지 않고 진행**할 수 있다. 대신 그 값이
수동이었다는 사실과 이유가 파일에 남아 나중에 설명할 수 있다.

## 장면 4 — 눈으로 먼저 확인한다 (1분) · 실물

기본 모드가 preview 다. 그냥 실행한다:

```bash
python solder/30_servo.py
```

**팔은 움직이지 않는다.** 화면에 팁 마커·타겟 마커·둘을 잇는 오차 화살표와
`err=NN mm` 가 뜬다. 타겟을 손으로 옮기면 화살표가 따라 도는 것을 보여준다.

말할 것: 자동으로 움직이기 전에 **로봇이 무엇을 보고 있는지 사람이 먼저 본다.**
오차 방향이 반대로 보이면 그건 게인 부호 문제이고, 그 상태로 서보를 걸면 팔이
발산한다. preview 는 그걸 팔이 아니라 화면에서 잡기 위한 단계다.

## 장면 5 — 비주얼 서보로 접촉 (2분) · 실물 · **핵심**

`--mode servo` 를 붙여 실행. Enter 를 눌러 시작한다.

```
  [0] err= 38.2mm  tip(+0.201,+0.004)  tgt(+0.233,-0.017)
  [1] err= 15.9mm  ...
  [2] err=  6.1mm  ...
  [3] err=  3.4mm  ★ xy 정렬 완료
  하강하며 접촉 탐색... baseline 41
    z=96mm  부하상승  +3
    z=92mm  부하상승  +9
    ★ 접촉 감지 — 유지 후 후퇴
```

말할 것: 오차가 **단조 감소**한다. 이게 폐루프의 증거다. 팁이 집게 어디에 어떤
각도로 붙었는지 저희는 **모릅니다** — 계산하지 않습니다. 카메라가 팁을 직접 보고
오차를 없애기 때문에 팁 오프셋이라는 값 자체가 필요 없습니다.

접촉 판정도 위치가 아니라 **부하**로 합니다. "z가 몇 mm면 닿는다"는 작업물 두께가
바뀌면 틀리지만, 부하가 뛰는 건 실제로 닿았을 때만 일어납니다.

→ 요구사항 **Vision 기반 제어 시나리오**.

## 장면 6 — 타겟을 옮긴다 (1분) · 실물

정렬이 도는 도중에 **타겟을 손으로 다른 자리로 옮긴다.** 다음 반복에서 오차가
다시 커지고, 팔이 새 자리로 따라간다.

말할 것: 타겟 좌표를 어디에도 저장하지 않습니다. **매 프레임 다시 읽습니다.**
그래서 "위치가 바뀌어도 동작한다"가 별도 기능이 아니라 구조에서 나옵니다.

## 장면 7 — 도달 한계 (1분) · 시뮬

타겟을 **작업영역 밖**에 놓거나:

```bash
python -m sorting.workspace --demo
```

```
  (+0.20, +0.00, +0.10)   통과   여유 89mm
  (+0.44, +0.00, +0.10)   거절   작업영역 밖 (140mm 벗어남)
```

서보 중이면 `goto()` 가 `OutOfReach` 를 받아 `safety.Stopped` 로 바꾸고 즉시 멈춘다.

말할 것: 거절할 때 **얼마나 벗어났는지**까지 알려줍니다. 그리고 이 검사는 IK 를
부르기 *전에* 돕니다 — 뒤에 있으면 아까 본 44cm 좌표가 그대로 통과합니다.

→ 요구사항 **로봇 제어 limit demo**.

## 장면 8 — 딜레이 보호장치 (2분)

**(a) 서보 루프 — 실물.** 카메라 브리지를 멈춘다.

```bash
pkill -f shm_bridge      # 또는 카메라 USB 분리
```

`safety.FrameWatchdog` 가 `frame_id` 가 300ms 넘게 안 바뀌는 걸 보고
`"카메라 프레임 지연/정지"` 로 서보를 중단시킨다. **오래된 프레임으로 팔을
움직이지 않는다.**

**(b) 단계적 대응 — 시뮬.** 분류 파이프라인 GUI 의 **[지연 주입]** 슬라이더:

| 슬라이더 | 화면 | 로봇 |
|---|---|---|
| ~200ms | 정상 | 그대로 진행 |
| 400ms | **경고** | 감속해서 계속 |
| 900ms | **보류** | 새 동작 시작 안 함 (하던 건 마무리) |
| 1800ms | **정지** | 즉시 정지 |

다시 슬라이더를 내리면 **한 단계씩** 회복된다 — 정지에서 정상으로 곧장 뛰지 않는다.

말할 것: 주입한 지연은 **실제 지연과 똑같은 경로**를 탑니다. 연출이 아닙니다.
회복을 천천히 하는 이유는, 깜빡임 한 번에 팔이 다시 출발하는 게 더 위험하기
때문입니다.

> 📌 **알려진 차이**: 4단계 워치독(`sorting/watchdog.py`)은 분류 파이프라인에
> 물려 있고, 서보 루프는 아직 이진 판정(`FrameWatchdog`)이다. 발표에서 이 차이를
> 숨기지 말고 "다음 단계"로 말하는 편이 낫다. `docs/DEV.md` 참고.

## 장면 9 — 긴급 정지 (30초) · 실물

정렬이 도는 한복판에 **Enter**(또는 Ctrl-C). 팔이 **그 자세 그대로** 선다.

말할 것: 토크를 끄지 않습니다. 끄면 중력으로 주저앉는데, **인두기를 물고 있으면
그게 작업면으로 떨어집니다.** 현재 위치를 목표로 다시 걸어 그 자리에 굳힙니다.
그리고 이동 대기 루프가 20ms 마다 확인하므로 **움직이는 도중에도** 섭니다.

→ 요구사항 **긴급 정지 버튼**.

## 장면 10 — 하드웨어가 바뀌면 (1분)

플래그 두 개만 붙인다. **소스는 건드리지 않는다.**

```bash
python solder/30_servo.py --mode servo --robot print --camera print --yes
```

같은 코드가 그대로 돈다. 시작할 때 무엇으로 도는지 먼저 찍고, 화면 대신
터미널에 무엇을 할지 출력된다.

```
──────────────────────────────────────────────────────────
  모드     servo
  로봇     print
  카메라   print
  ⚠️  print 드라이버 사용 중 — 실제 하드웨어는 움직이지 않습니다
──────────────────────────────────────────────────────────
[로봇] 이동 → (+0.200, -0.012, +0.100)m  [아래보기]
[카메라] 프레임 1 합성 — 공 2개, 구역 2개 (깊이 없음)
```

말할 것: 위쪽 코드는 하드웨어를 **이름으로만** 압니다. 요구하는 것이
`sorting/ports.py` 에 계약으로 적혀 있고, 새 장비는 어댑터 한 개로 붙습니다.

그리고 플래그로 받는 이유가 있습니다. 소스를 고쳐서 바꾸면 **되돌리는 걸 잊기
쉽고**, 그 상태로 다음 시연이 돌아 "로봇이 왜 안 움직이지"가 됩니다. 플래그는
그 실행에만 적용되고, 시작 배너가 항상 무엇으로 도는지 알려줍니다.

## 실패했을 때의 대비

| 만약 | 이렇게 |
|---|---|
| 카메라 브리지가 안 뜸 | `--camera replay` 로 저장된 사진 재생 |
| 로봇이 응답 안 함 | `--robot print` 또는 `--sim`(헤드리스 시뮬) |
| 마커를 못 잡음 | `lab_tuner.py` 로 그 자리에서 재측정 → `TIP_LAB`/`TARGET_LAB` |
| 서보가 발산함 | `GAIN` 부호 반전. 진동하면 `GAIN` 낮춤 |
| 접촉이 너무 일찍/늦게 | `safety.LOAD_CONTACT` 를 하강 로그 값 사이로 |
| 캘리브레이션이 깨짐 | `calib set` 으로 수동 입력 (장면 3 이 곧 대비책) |
| `H.npy` 가 없음 | `vision/03_calib_auto.py` 재실행 (카메라 움직였으면 필수) |

**어떤 실패든 그 자체가 시연 소재가 된다** — 이 시스템은 그런 상황을 다루도록
만들어졌기 때문이다.
