# 데모 시나리오

**총 10분.** 위험한 것(도달 한계·딜레이)은 시뮬로, 설득력이 필요한 것(비전·
티칭·E-STOP)은 실물로 보여준다.

## 준비 (시연 전날 / 당일 아침)

```bash
./hp60c-camera/scripts/start_bridge.sh      # 'Streaming started' 확인
python -m sorting.calib report              # 미측정 값이 없는지 확인
```

`calib report` 가 전부 ✅/✏️ 면 준비 끝. ⚠️ 가 남아 있으면 그 줄에 적힌 명령으로
재고 시작한다. **이 확인을 건너뛰면 데모 중에 "왜 안 움직이지"가 된다.**

빈 작업면에서 **E-STOP 이 실제로 듣는지 먼저 확인**한 뒤 공을 올린다.

---

## 장면 1 — 작업영역을 손으로 가르친다 (1분 30초) · 실물

> "로봇이 어디까지 가도 되는지를 저희가 숫자로 정하지 않았습니다. 직접 재게 했습니다."

```bash
python -m sorting.teach limits
```

토크가 꺼지고 팔이 자유로워진다. **안전하다고 판단하는 범위의 테두리를 손으로
천천히 한 바퀴** 돌면, 10Hz 로 손끝 좌표가 기록되어 그 모양 그대로 영역이 된다.

말할 것: 운동학 IK 는 반경 0.44m 까지 잔차 0mm 로 푼다. 즉 IK 만 믿으면 한계가
사실상 없다. 하지만 그렇게 뻗은 자세는 서보 부하가 크고 정밀도가 떨어진다.
**운동학적 한계와 운용상 안전 한계는 다르고, 후자는 재야 안다.**

## 장면 2 — 좌표를 손으로 가르친다 (1분) · 실물

```bash
python -m sorting.teach heights     # 팔끝을 책상·bin 에 대고 Enter
python -m sorting.teach add bin_red
```

화면 오른쪽 상태창에 **"미측정 값 N개"** 가 줄어드는 걸 보여준다.

말할 것: 티칭으로 얻은 좌표와 비전이 찾아낸 좌표가 **같은 파이프라인**으로
들어간다. 사람이 가르친 것과 카메라가 본 것이 같은 좌표계에서 만난다.

## 장면 3 — 측정이 실패하면 (1분) · 실물

> "현장에서 서보가 말을 안 들으면 어떻게 하죠?"

일부러 실패 상황을 만들거나(케이블 분리) 이미 겪은 상황을 이야기한 뒤:

```bash
python -m sorting.calib set robot.z_grasp 0.008 --note "서보4 무응답 — 자로 측정"
python -m sorting.calib report        # ✏️ 수동 으로 표시되고 사유가 남는다
```

말할 것: 자동 측정이 막혀도 **막히지 않고 진행**할 수 있다. 대신 그 값이
수동이었다는 사실과 이유가 파일에 남아 나중에 설명할 수 있다.

## 장면 4 — 자동 분류 (2분) · 실물

```bash
python sorting_main.py --real --slow
```

[분류 시작]. 카메라 화면에 공·bin·**작업영역 경계선**이 함께 보인다.

## 장면 5 — 구역을 옮긴다 (1분) · 실물

돌아가는 중에 **bin 을 손으로 다른 자리로 옮긴다.** 화면의 상자와 좌표가 따라
움직이고, 다음 공은 새 자리로 간다.

말할 것: bin 좌표를 어디에도 저장하지 않는다. 놓기 직전에 그 프레임에서 다시
읽는다. 그래서 "위치가 바뀌어도" 가 별도 기능이 아니라 구조에서 나온다.

## 장면 6 — 도달 한계 (1분 30초) · 시뮬

```bash
python -m sorting.workspace --demo
```

또는 GUI 에서 영역 밖에 공을 놓는다 → **회색 X 와 "범위 밖"** 표시, 집으러 가지
않는다.

```
  (+0.20, +0.00, +0.10)   통과   여유 89mm
  (+0.44, +0.00, +0.10)   거절   작업영역 밖 (140mm 벗어남)
```

말할 것: 거절할 때 **얼마나 벗어났는지**까지 알려준다. 그리고 이 검사는 IK 를
부르기 *전에* 돈다 — 뒤에 있으면 의미가 없다.

## 장면 7 — 딜레이 보호장치 (2분) · 시뮬

GUI 의 **[지연 주입]** 슬라이더를 천천히 올린다.

| 슬라이더 | 화면 | 로봇 |
|---|---|---|
| ~200ms | 정상 | 그대로 진행 |
| 400ms | **경고** | 감속해서 계속 |
| 900ms | **보류** | 새 동작 시작 안 함 (하던 건 마무리) |
| 1800ms | **정지** | 즉시 정지 |

다시 슬라이더를 내리면 **한 단계씩** 회복된다 — 정지에서 정상으로 곧장 뛰지
않는다.

말할 것: 주입한 지연은 **실제 지연과 똑같은 경로**를 탄다. 연출이 아니라
보호장치가 진짜로 동작하는 것이다. 그리고 회복을 천천히 하는 이유는, 깜빡임
한 번에 팔이 다시 출발하는 게 더 위험하기 때문이다.

## 장면 8 — 긴급 정지 (30초) · 실물

동작 한복판에 **[Space]** 또는 E-STOP 버튼. 팔이 **그 자세 그대로** 선다.

말할 것: 토크를 끄지 않는다. 끄면 중력으로 주저앉아 오히려 위험하고 집고 있던
공도 떨어진다. 현재 위치를 목표로 다시 걸어 그 자리에 굳힌다.
그리고 이동 대기 루프가 20ms 마다 확인하므로 **움직이는 도중에도** 선다.

## 실패했을 때의 대비

| 만약 | 이렇게 |
|---|---|
| 카메라 브리지가 안 뜸 | `--replay shots` 로 저장된 사진 재생 |
| 로봇이 응답 안 함 | `--sim` 으로 전환, 시뮬로 계속 |
| 캘리브레이션이 깨짐 | `calib set` 으로 수동 입력 (장면 3 이 곧 대비책) |
| 조명이 달라 검출 불안정 | `lab_sample` 로 그 자리에서 재측정 |

**어떤 실패든 그 자체가 시연 소재가 된다** — 이 시스템은 그런 상황을 다루도록
만들어졌기 때문이다.
