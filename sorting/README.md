# SO-ARM101 색 분류 스테이션 (`sorting/`)

카메라로 빨간공·파란공을 찾아 색에 맞는 구역에 담는 로봇 시스템.
**구역을 책상 위에서 옮겨도 다음 공은 새 자리로 간다** — 좌표를 어디에도
저장해두지 않기 때문이다.

> **이 저장소에서의 위치**
> 기존 실습 파일(`vision/`, 루트의 `01_load.py`~, 루트 `README.md`)은 **하나도
> 건드리지 않았다.** 이 시스템은 `sorting/` 패키지 + `sorting_main.py` +
> `firmware/` + `tests/` 로만 이루어져 있어, 기존 코드와 나란히 둔 채 쓸 수 있다.
> `soarm_lab/` 과 `hp60c-camera/` 도 제공물 그대로 쓴다(수정 없음).
> 촬영샷은 저장소에 이미 있는 `shots/` 를 그대로 재사용한다.

## 과제 요구사항 ↔ 구현

| 요구사항 | 구현 | 파일 |
|---|---|---|
| 빨간공·파란공을 색에 맞는 영역으로 분류 | CIELAB 색 검출 + 상태머신(집기→확인→놓기) | [vision.py](vision.py) · [pipeline.py](pipeline.py) |
| Vision 기반 로봇제어 | 픽셀 → 4점 호모그래피 → 로봇좌표 → IK | [mapping.py](mapping.py) · [calibrate.py](calibrate.py) |
| **place 위치가 바뀌어도 거기에 놓기** | bin 도 공과 같은 방식으로 **매 사이클 재검출**. 좌표를 저장하지 않음 | [pipeline.py `_bin_xy`](pipeline.py) |
| 표현 수단 (가점) | 라이브 오버레이 · 3D 트윈 · 통계 · 부저 2성부 · 완료 세리머니 | [gui/](gui/) · [sound.py](sound.py) |

추가로 넣은 것: **깊이 기반 안전 경계선**(사람 손이 들어오면 경고음과 함께 정지,
빠지면 재개음과 함께 재시작), 파지 실패 재시도, 검출 안정화, FPS·지연 표시.

## 어떻게 "위치가 바뀌어도" 되는가

핵심은 한 문장이다.

> 공도 구역도 "그 색 픽셀 덩어리"다. 둘을 가르는 건 색이 아니라 **크기와 모양**이다.

- 빨간 bin = 가장 큰 빨간 덩어리, 파란 bin = 가장 큰 파란 덩어리
- 공 = 면적이 작고 **원형도(4πA/P²)가 높은** 덩어리
- 주황 구역 = 공이 놓여 있는 공급 구역. 이 안의 공만 집는다

구역 좌표는 변수에 담아두지 않고 **놓기 직전에 그 프레임에서 다시 읽는다**. 그래서
사이클 도중 구역을 옮겨도 다음 공은 새 자리로 간다. 이 동작은 자동 테스트로
고정해 두었다 → `test_place_follows_moved_bin`.

원형도로 거르는 근거는 실측이다. `shots` 8장에서 진짜 공은 원형도
0.85~0.90, 빨간 과자봉지 같은 잡동사니는 0.67 이하로 깨끗이 갈린다. 면적과 달리
카메라 높이가 바뀌어도 변하지 않는 값이라 더 믿을 만하다.

## 색은 왜 CIELAB 인가

색 판정은 HSV 가 아니라 **Lab 의 a*/b* 평면에서 기준색까지의 거리**로 한다.

```python
RED = LabColor("red", a=+34.0, b=+7.0, radius=12.0, ...)   # config.py
```

`shots` 8장에서 잰 실측값이 이유를 그대로 보여준다.

| 빨강 기준색 (+34, +7) 에서의 거리 | 빨간 공 | 빨간 과자봉지 | 파란 공 |
|---|---|---|---|
| a*/b* 평면 거리 | **0 ~ 2** | **16.3 ~ 17.7** | 44.7+ |

HSV 시절에는 과자봉지도 '빨강' 마스크를 그냥 통과해서, 공이 아니라는 판단을
면적·원형도에 전적으로 기대야 했다. Lab 에서는 **색 단계에서 이미 갈린다**
(반경 12 vs 거리 16.3). 모양 필터는 이제 보조수단이다.

그 밖에 실무적으로 편해지는 점 둘:

- **빨강이 쪼개지지 않는다.** HSV 색상환에서 빨강은 0°와 180° 양끝에 걸쳐 있어
  범위를 두 개로 나눠 OR 해야 했다. 거리 판정에는 그 이음매가 없다.
- **캘리브레이션이 클릭 한 번이다.** 슬라이더 6개(H/S/V 상·하한) 대신
  `python -m sorting.lab_sample` 로 대상을 클릭하면 붙여넣을 한 줄이 나온다.

### 스레드

Qt 메인 스레드는 **그리기만** 한다. 카메라도 로봇도 블로킹 I/O라 하나라도
메인에 두면 창이 얼고, 그러면 E-STOP 버튼조차 안 눌린다.

```
[CameraWorker]  읽기 → 검출 → 트래킹 → 안전감시  ──sceneReady──▶ [메인] 그리기
[PipelineWorker] 상태머신 + 로봇 시리얼 (단독 소유) ──joints──▶ [메인] 3D 트윈
```

로봇 시리얼(`/dev/ttyACM0`)은 PipelineWorker 만, 부저 시리얼은 sound 워커만
만진다. `driver_sdk` 는 sync write 없이 관절마다 개별 write 를 하므로 두
스레드가 동시에 쓰면 패킷이 섞인다.

E-STOP 만은 예외로 메인 스레드에서 로봇을 직접 친다. 큐에 넣고 워커 차례를
기다리면, 그 워커가 마침 이동 대기 중일 때 정지가 늦기 때문이다.

## 부저 (Arduino Uno)

```
Uno D9  (Timer1) ── 피에조 A ── GND     멜로디
Uno D10 (Timer2) ── 피에조 B ── GND     화음/베이스
(각 부저에 직렬 100~220Ω 권장)
```

Arduino 내장 `tone()` 은 타이머를 공유해 **동시에 한 음만** 낸다. 그래서
`buzzer.ino` 는 Timer1/Timer2 를 직접 잡아 두 핀에 독립된 구형파를 낸다.
Timer0 은 `millis()` 가 쓰므로 건드리지 않는다.

PC 는 `PLAY:victory` 한 줄만 보내고 악보는 보드 안에 있다 — 3초짜리 팡파레가
울리는 동안에도 로봇 제어 루프는 전혀 기다리지 않는다.

**곡 바꾸기**: `tunes.py` 와 `firmware/buzzer/buzzer.ino` 의 악보
문자열만 고치면 된다. 표기법은 `"C5-8 E5-16 R-4"` (음이름옥타브-분음표, R=쉼표,
`.`=점음표).

> `KIRBY_CLEAR` 는 별의 커비 스테이지 클리어 곡을 **기억에 의존해 옮긴 초안**이라
> 음정이 정확하지 않을 수 있습니다. `python -m sorting.sound --test kirby --pc` 로
> 들어보고 그 두 줄만 고치면 됩니다. 파이썬과 펌웨어의 음정 계산이 어긋나지
> 않는지는 `test_tunes.py` 가 자동으로 검사합니다.

## 안전 설계

**경계선 방식**을 쓴다. 로봇팔도 책상 위에 떠 있어서 "테이블보다 높은 것"을
전부 침입으로 보면 로봇 자신이 계속 걸린다. 대신 **로봇이 절대 넘지 않는
바깥 띠**만 감시한다. 팔은 띠 안쪽에서만 움직이고 사람 손은 반드시 띠를 통과해
들어오므로, 손이 팔에 닿기 전에 잡힌다. 산업용 안전펜스와 같은 원리다.

- 색이 아니라 **깊이**를 쓴다 → 피부색·장갑·소매 색을 가리지 않는다
- 판정 임계값은 **띠 면적 대비 비율** → 깊이 해상도가 바뀌어도 감도가 유지된다
- **히스테리시스**: 들어오는 판정(2프레임)보다 나가는 판정(8프레임)을 더 까다롭게
  → 깜빡임 한 번에 로봇이 섰다 갔다 하지 않는다
- **이동 중에도** 감지된다. `move_to` 의 도착 대기 루프가 매 20ms 중단 조건을
  확인한다 — 이게 없으면 한 동작이 끝날 때까지 손이 들어와도 못 알아챈다
- E-STOP 은 **토크를 끄지 않는다.** 끄면 팔이 중력으로 주저앉아 오히려 위험하다.
  현재 위치를 목표로 다시 걸어 그 자리에 굳힌다
- 경계선이 설정되지 않았으면 GUI 가 "안전감시 꺼짐"을 눈에 띄게 표시하고
  시작 전에 한 번 더 묻는다 — 없는 안전장치가 있는 척하지 않기 위해

## soarm_lab 을 고치지 않고 메운 공백

`soarm_lab/` 과 `hp60c-camera/` 는 제공물 그대로 복사해 **수정하지 않았다.**
다만 그대로는 이 과제를 지탱하지 못하는 곳이 세 군데 있어 `sorting/robot.py`
에서 감쌌다.

| 제공 코드의 상태 | 왜 문제인가 | 대응 |
|---|---|---|
| `Arm.run()` 이 `_backend(False)` 고정 | 시뮬 전용 — `pick_place.py` 순서표로는 실물이 안 움직인다 | 시뮬·실물 공용 시퀀서를 새로 작성 |
| `SimBackend.move()` 가 `time.sleep` 블로킹 | GUI 스레드에서 부르면 창이 언다 | 논블로킹 `LiveSim` 을 헤드리스로 사용 |
| `RealBackend.move()` 가 그리퍼(id 6) 미처리 | 주석만 있고 구현이 없어 실물로는 공을 못 잡는다 | `JOINT_LIMITS[6]` 의 percent 매핑을 구현 |

`ADDR_MOVING`(66) 도 상수만 있고 접근자가 없어, 도착 판정에 직접 읽어 쓴다
(실패하면 위치 폴링으로 폴백).

## ⚠ 실측으로 맞춰야 하는 값

**이 저장소의 기본값 중 일부는 다른 환경에서 찍은 사진과 다른 로봇 기준이다.**
설치 현장에서 반드시 다시 재야 하는 것들을 우선순위 순으로 정리한다.

### 1. 반드시 재야 함 (안 재면 동작하지 않음)

| 대상 | 방법 | 저장 위치 |
|---|---|---|
| **픽셀 → 로봇 좌표 (H)** | `python -m sorting.calibrate` — 공을 네 곳에 옮기며 팔끝을 대준다 | `data/H.npy` |
| **안전 경계선 + 테이블 기준면** | `python -m sorting.setup_zone` — 로봇 작업범위를 클릭, 빈 테이블 촬영 | `data/safety_zone.json`, `data/depth_baseline.npy` |
| **주황 공급구역 색** | `python -m sorting.lab_sample` — 구역을 클릭 | `config.py` 의 `ORANGE` |

`ORANGE` 는 촬영샷에 주황 물체가 없어 **실측하지 못한 추정값**이다
(`a=+25, b=+45`). 공급구역을 쓰려면 반드시 다시 재야 한다. 재기 전까지는
`config.py` 에서 `PICK_ZONE = None` 으로 두면 화면 전체에서 공을 찾는다.

H 는 재투영 최대오차가 **10mm 미만**이어야 한다. 그보다 크면 네 점이 한쪽에
몰린 것이니 작업면 네 귀퉁이에 가깝게 다시 잡는다.

### 2. 조명·공이 바뀌면 다시 재는 게 좋음

| 대상 | 현재값 | 근거 | 다시 재는 법 |
|---|---|---|---|
| `RED` 기준색 | a=+34, b=+7, r=12 | shots 8장 실측 | `lab_sample` 로 공 클릭 |
| `BLUE` 기준색 | a=+6, b=−29, r=16 | shots 8장 실측 | 〃 |
| `min_area_ball` / `max_area_ball` | 300 / 6000 px | 그 촬영거리에서 공이 ~1,100px | 카메라 높이가 다르면 비례해서 조정 |
| `min_area_region` | 8000 px | 공 상한보다 위여야 구역과 안 헷갈림 | `max_area_ball` 보다 크게 유지 |

`min_circularity`(0.75)는 카메라 높이에 불변이라 대개 그대로 둬도 된다.

### 3. 로봇 개체차 — 실물 팔이 바뀌면 확인

| 값 | 현재값 | 왜 개체마다 다른가 |
|---|---|---|
| `ball_radius` | 0.02 m | 쓰는 공 크기에 맞춘다 (접근점 계산에 직접 들어감) |
| `z_grasp` | 0.005 m | 책상 높이·그리퍼 마모에 따라 다르다. 너무 낮으면 책상을 긁는다 |
| `grip_closed` | 15 % | 공 지름에 맞춘다. 공이 튕겨나가면 값을 올린다 |
| `grip_empty_pct` | 8 % | **파지 성공 판정 기준.** 빈 손으로 닫았을 때 읽히는 값보다 조금 위로 |
| `home_pose_deg` | (0,30,−45,0,0) | 카메라·구역 배치에 팔이 걸리지 않는 자세로 |

`grip_empty_pct` 를 정하는 법: 수동 모드에서 그리퍼를 **아무것도 없이** 완전히
닫고, 그때 화면에 읽히는 개도(%)를 확인한다. 그 값 + 3~5 정도로 잡으면 된다.
공을 물었을 때는 공 두께만큼 덜 닫히므로 이 값보다 크게 나온다.

`data/` 안의 캘리브레이션 산출물은 설치마다 다르므로 **git 에 올리지 않는다**
(`.gitignore` 에 이미 들어 있다). 새 환경에서는 위 ①번을 처음부터 다시 한다.

### 4. 부저 음정 (선택)

`tunes.py` 의 `KIRBY_CLEAR` 는 **기억에 의존해 옮긴 초안**이라 음정이
틀릴 수 있다. `python -m sorting.sound --test kirby --pc` 로 들어보고 그 두 줄만
고치면 된다. 파이썬과 펌웨어의 음정 계산이 어긋나지 않는지는
`test_tunes.py` 가 자동으로 검사하므로, 고친 뒤 `pytest` 를 한 번 돌리면 된다.

## 증상별 튜닝

| 증상 | 볼 곳 |
|---|---|
| 공을 놓친다 / 깜빡인다 | `RED`·`BLUE` 의 `radius` 를 키운다, `min_area_ball` 을 낮춘다 |
| 엉뚱한 걸 공으로 잡는다 | `radius` 를 줄인다 → 그래도 남으면 `min_circularity` 를 올린다 |
| 두 색이 서로 헷갈린다 | `lab_sample` 로 둘을 재서 거리를 본다. 8 미만이면 경고가 뜬다 |
| 그늘에서만 안 잡힌다 | `l_min` 을 낮춘다 (기본 25) |
| bin 을 못 찾는다 | `min_area_region` 을 낮춘다 |
| 사람 감지가 너무 예민/둔하다 | `min_band_fraction`, `intrusion_mm` |
| 팔이 공을 밀어낸다 | `z_grasp`, `grip_closed` |
| 파지 성공인데 실패로 뜬다 | `grip_empty_pct` (위 3번 참고) |
